# Code Audit — 2026-10-09

Source: a read-only review of the whole repo after the Boomschors.nl rebrand (master `f5bbf39`, 248 tests).
Scope: **bugs and correctness, security and privacy, dead code and simplification.** Cost and performance were out of scope, except where they fall out of a correctness finding.
Method: three parallel review passes (bugs, security/privacy, dead code). Every finding then went through an adversarial verification pass, which reproduced it with the Flask `test_client` (keys blanked, outbound calls stubbed) or confirmed it from the code. Each finding below is marked **CONFIRMED** (reproduced or unambiguous in the code) or **PLAUSIBLE** (the code is clear, but the impact depends on something that could not be checked offline). Cited lines were spot-checked again while this report was written. Findings that more than one pass reported are merged and listed once.

**Headline:** 41 unique findings. 3 HIGH (one of them PLAUSIBLE), 16 MEDIUM, 22 LOW. About 400 lines can be cut.
The pattern behind most of the MEDIUM findings is the one CLAUDE.md already warns about: **paths that return before the router or before `_start_handoff`**, and canned replies that skip `_remember_turn`.

> Disclosure from the verification pass: one local probe ran before the keys were blanked and made a single read-only StatusWeb lookup for `400000001`. No OpenAI call was made and no email was sent.

## 2. All findings by area

### Bugs & correctness

- **HIGH · CONFIRMED · C1 · Escalation email drops the question and phone number.** [backend/email_client.py:85](backend/email_client.py#L85)
  *Failure:* "Ik wil mijn bestelling annuleren, het is BS12345" → "Jan" → "jan@example.nl" → "Bel me op 0612345678" sends two emails. Neither contains the request, the BS number or the phone number. Reproduced: both calls received `history=[]`.
  *Fix:* write `question` and the name into the body, as `zendesk_client.py:91` already does. Append the triggering message to `chat_history` before `_start_handoff`. Move the transcript building into one helper shared by both clients. Test: patch `requests.post` and assert that the question and a forwarded phone number appear in `payload['text']`.

- **HIGH · CONFIRMED · C2 · Tests hit live services.** [backend/tests/conftest.py:16](backend/tests/conftest.py#L16)
  *Failure:* `python -m pytest` with a filled `.env` sends a real escalation email, bills OpenAI for every fall-through message, and sends StatusWeb lookups for fake 8+ digit numbers.
  *Fix:* before `import app`, set `OPENAI_API_KEY`, `SHIPPING_API_KEY`, `MAILERSEND_API_KEY`, `SMTP_*`, `ZENDESK_*` and `SHOPIFY_STOREFRONT_TOKEN` to `''`. `load_dotenv` does not override existing variables. Replace the `generate_response` mocks with `get_answer`/`extract_name` mocks.

- **MEDIUM · CONFIRMED · C6 · Handoff entry points that bypass `_start_handoff`.** [backend/app.py:2093](backend/app.py#L2093)
  *Failure:* a session with `handoff_done=True` and name "Jan" sends "dit is belachelijk", or fails twice in tracking. The bot asks "Mag ik je naam...?" and a second escalation follows.
  *Fix:* `_start_handoff(lang, user_message, opening=<existing copy>, reason='frustration'|'loop'|'flow_dead_end')`. Its docstring already lists these callers.

- **MEDIUM · CONFIRMED · `flow_attempts` survives a successful flow.** [backend/app.py:1412](backend/app.py#L1412)
  *Failure:* "Waar is mijn pakket?" → "eh momentje" → "400000001" (status shown) → "Waar blijft mijn andere zending?" → "even zoeken" escalates on the first miss of the new flow.
  *Fix:* pop `flow_attempts` in `_clear_tracking_state` (:1553) and `_clear_shopify_verification_state` (:1566), and reset it when a flow is entered.

- **MEDIUM · CONFIRMED · Offering your own phone number during the handoff cancels it.** [backend/app.py:1502](backend/app.py#L1502)
  *Failure:* in `awaiting_email`, "Ik heb geen mail, je kunt mij telefonisch bereiken op 0612345678" returns *our* number and wipes the state to `{'state':'inactive'}`. The handoff is gone and the customer's number goes nowhere. The `je` alternative in `PHONE_CONTACT_RE` ([:472](backend/app.py#L472)) also matches "Mag ik je mijn telefoonnummer geven?", which brings back what `0dfa43c` set out to prevent.
  *Fix:* inside `awaiting_name`/`awaiting_email`, check `PHONE_NUMBER_RE` first and forward a supplied number as contact info. Drop `je` from the possessive alternative. Never wipe the handoff on a mention of the phone.

- **MEDIUM · CONFIRMED · The dead-end loop detector fires on ordinary answers that mention the contact email.** [backend/app.py:904](backend/app.py#L904)
  *Failure:* two normal answers that cite klantenservice@boomschors.nl (which the prompt tells the model to do) make every later message get the frustration copy. After "nee" it fires again, because the decline is never appended and the 10-turn window does not move.
  *Fix:* require the *last two* assistant turns to be dead ends, or match only the canned fallback phrasing. Record declines in the history.

- **MEDIUM · CONFIRMED · The inline `order_match` enters the WISMO postcode flow in production.** [backend/app.py:1958-1960](backend/app.py#L1958)
  *Failure:* "Kan ik bestelling 12345 zelf afhalen?" and "Ik plaats een bestelling 5 m3 Frans boomschors, wat kost dat?" both get "Dat kan ik voor je opzoeken! Wat is de postcode...?". It overrides the pickup route from `afa817b` and ignores `_stock_lookup_enabled()`.
  *Fix:* see the Shopify cut in section 3. At minimum, run it only when `intent == 'tracking'` and require 4+ digits.

- **MEDIUM · CONFIRMED · `TRACKING_INTENT_RE` and `ESCALATE_TOPIC_RE` misroute pre-purchase questions.** [backend/app.py:349](backend/app.py#L349)
  *Failure:* "Wanneer kunnen jullie leveren in Friesland?" → tracking (asks for the shipment number). "Ik heb maar 3 kuub nodig, wat kost dat?" → escalate_topic (manco pattern on "maar").
  *Fix:* drop or narrow `wanneer kunnen`/`wanneer wordt` (require mijn/onze plus an order noun). Anchor the manco pattern to delivery verbs. Re-run over all chat-export messages (see the pattern memory).

- **MEDIUM · CONFIRMED · While a shipment number is awaited, any 4–7 digit number or date is taken as one.** [backend/app.py:416](backend/app.py#L416)
  *Failure:* "Wat kost 1000 liter boomschors?" → "Je bestelnummer (1000) heb ik ontvangen...". "ik heb op 12-05-2026 besteld" → `('12052026', True)`, which triggers a StatusWeb lookup.
  *Fix:* run `classify_intent` (or at least question detection) before extraction. Ignore numbers followed by a unit and date-shaped strings.

- **MEDIUM · CONFIRMED · The guided-flow escape hatch is a second, competing router.** [backend/app.py:1330](backend/app.py#L1330)
  *Failure:* while `awaiting_order_number`, "jullie telefoon werkt niet" gets the phone number (outside a flow it is escalate_topic). "ik wil mijn bestelling annuleren" and "de zakken kwamen kapot aan" get "Ik zie geen zendingnummer". `order_admin` and `escalate_topic` are never checked inside a flow. The phone check is copied 4 times (1332, 1440, 1501, 2083), each at a different priority.
  *Fix:* compute `classify_intent` once at the top of `_handle_chat` with a deliberate `phone` label. Escape when `intent in {human_request, order_admin, escalate_topic, phone}` or on frustration. Keep one phone block.

- **MEDIUM · CONFIRMED · Most canned early returns still skip `_remember_turn`.** [backend/app.py:1785](backend/app.py#L1785)
  *Failure:* after "Waar is mijn pakket?" → "400000001", `chat_history` has length 0. A follow-up "Kan dat ook eerder?" is reformulated without context. This also keeps `user_turns_so_far` low and empties the escalation history (C1). Only the phone paths call it (1335, 1443, 1504, 2086).
  *Fix:* send every canned return through one helper that appends, saves and logs. Add a test that walks each branch and asserts the history grows.

- **MEDIUM · CONFIRMED · `compute_volume` treats a unit-less count as metres.** [backend/volume_calc.py:95](backend/volume_calc.py#L95)
  *Failure:* "hoeveel bigbags voor 2 borders van 10 m bij 1 m?" → "2 m x 10 m x 1 m = 20 m3", injected as "REKENHULP (al voor je uitgerekend en correct)".
  *Fix:* require a unit on every dimension, or allow only a depth followed by dik/diep/laag to be unit-less. Return `None` when a number is followed by a noun.

- **MEDIUM · PLAUSIBLE · StatusWeb classification marks "niet afgeleverd" and "wordt bezorgd" as delivered.** [backend/shipping_api.py:223](backend/shipping_api.py#L223)
  *Failure:* StatusOmschrijving "Niet afgeleverd - klant niet thuis" gives "✅ Je zending is afgeleverd! 🎉". Unknown descriptions default to `in_transit` (:229). Whether StatusWeb actually returns these texts was not checked.
  *Fix:* check negations and future forms first, or map on `StatusNummer`. Default unknown statuses to the neutral "Status zending: <desc>" branch.

- **MEDIUM · CONFIRMED · `generate_helpful_unknown_response` bypasses `check_output`.** [backend/app.py:2171](backend/app.py#L2171), [backend/rag_engine.py:1439](backend/rag_engine.py#L1439)
  *Failure:* every `__UNKNOWN__` answer comes from a second generation at temperature 0.7 that goes to the customer unfiltered: no gate for foreign script, system vocabulary or wrong language, and no tutoyeer rule. Whether the model actually emits bad output here was not reproduced.
  *Fix:* pass the result through `check_output` and `_safe_fallback`, or move the gate into one shared `_complete()` helper.

- **MEDIUM · CONFIRMED · `.env.example` sets `BRAND_PERSONALITY_NL/EN` to an older persona.** [backend/.env.example:130](backend/.env.example#L130)
  *Failure:* following the README (`cp .env.example .env`, docker-compose loads it) gives a local bot without the no-repeat, decline and one-upsell rules. Local replays and `evaluate_rag` runs then disagree with production.
  *Fix:* comment out `BRAND_PERSONALITY_*`, `BRAND_ASSISTANT_NAME` and `BRAND_WELCOME_EN`, with a note pointing to the defaults in `brand_config.py`.

- **LOW · CONFIRMED · `CLOSING_RE` answers "oké" with "Graag gedaan" even when it is a yes to the bot's offer.** [backend/app.py:2131](backend/app.py#L2131)
  *Failure:* the bot asks "Wil je dat ik een collega laat meekijken?", the customer says "Oké", and the bot replies "Graag gedaan!" with no handoff.
  *Fix:* skip the closing shortcut when the last assistant turn ended with a question. When that question offered a colleague, route to `_start_handoff`.

- **LOW · CONFIRMED · `handoff_done` is set even when the escalation failed.** [backend/app.py:1370](backend/app.py#L1370)
  *Failure:* the send fails, the customer sees "Sorry, er ging iets mis", asks again for a medewerker, and is told "Je bericht staat al bij een collega".
  *Fix:* set `handoff_done` only when `result` is truthy (and see C4).

- **LOW · CONFIRMED · A transient embedding failure leaves a file permanently missing chunks.** [backend/rag_engine.py:513](backend/rag_engine.py#L513)
  *Failure:* a 429 during reindexing drops one chunk. `chunk_0` still carries the full-file `content_hash`, so every later boot skips the file.
  *Fix:* return a success flag from `_ingest_text_chunks`. On any failure, delete the file's chunks (or omit the hash) so the next boot retries.

- **LOW · CONFIRMED · The chunker sometimes emits a duplicate tail chunk.** [backend/rag_engine.py:516](backend/rag_engine.py#L516)
  *Failure:* this happens only when the last chunk ends within 200 chars of the end of the text. It applies to 4 of 42 KB files today (certificaten_en_keurmerken, Gronddoekpennen, Houtmulch, niet_leverbare_producten). `chunk_1` repeats `[1800:end]` and takes one of that source's 2 diversity slots.
  *Fix:* break when `end >= text_len` before subtracting the overlap. Note that existing chunks are not rebuilt unless the file's hash changes.

- **LOW · PLAUSIBLE · The `save_session_state` temp file is per process, not per thread.** [backend/app.py:950](backend/app.py#L950)
  *Failure:* two concurrent saves of one session (a duplicated tab) share `<id>.json.tmp.<pid>`. The second `os.replace` raises `FileNotFoundError`, or the JSON comes out interleaved. Not reproduced.
  *Fix:* `tempfile.NamedTemporaryFile(dir=SESSION_DIR, delete=False)`, or add the thread id or a uuid to the name.

- **LOW · PLAUSIBLE · An email given inside a sentence is rejected forever.** [backend/app.py:1506](backend/app.py#L1506)
  *Failure:* "mijn mail is jan@example.nl" fails the anchored `EMAIL_REGEX`, gets "Hmm, dat lijkt niet helemaal te kloppen", and there is no attempt counter. The exact path depends on the LLM's `detect_ticket_intent` label.
  *Fix:* extract the first email-shaped substring before validating. Offer the phone number after two misses.

- **LOW · CONFIRMED · The portal shows every conversation as NL, and the EN filter is always empty.** [portal/js/storage.js:187](portal/js/storage.js#L187)
  *Failure:* nothing writes `conversation_metadata.language`. The portal only PUTs `rating` and `status`, and `admin_conversations` never reads the session's language.
  *Fix:* add `"lang"` to each `_log_chat_message` entry and derive it in `admin_conversations`, or delete the language badge, filter and setting.

### Security & privacy

- **HIGH · PLAUSIBLE · C3 · Rate limits keyed on the proxy IP.** [backend/app.py:182](backend/app.py#L182)
  *Failure:* (a) one script sending 30 POSTs/min blocks chat for all customers; (b) after 50 `/widget.js` loads in an hour the widget does not render; (c) 10 wrong logins/min lock the admin out. The admin-access log lines (302-305, 2241-2258) record the proxy IP. In a test context with `REMOTE_ADDR=100.64.0.2` and `X-Forwarded-For=1.2.3.4`, the key was `100.64.0.2`. Months without a missing-widget report suggest traffic stays low or the edge uses several IPs.
  *Fix:* first check the Railway access log. If confirmed, use `ProxyFix(app.wsgi_app, x_for=1, x_proto=1)` (exactly 1 hop, so the header cannot be spoofed) and `@limiter.exempt` on `/widget.js` and `/health`.

- **MEDIUM · CONFIRMED · C5 · Shared `unknown_session`, and any client-chosen ID is accepted.** [backend/app.py:1192](backend/app.py#L1192)
  *Failure:* customer B (null ID) asks for a colleague and gets "Ik pak dit op met een collega, Jan de Vries. Wat is je e-mailadres?". B's phone number is forwarded with A's name and email. Anyone can POST `session_id='unknown_session'` and the model then receives other customers' last 10 messages. `sanitize_session_id` also maps punctuation-only IDs to a shared `.json`. The log `chat_unknown_session.json` never ages out, because its mtime keeps moving.
  *Fix:* reject a missing or invalid ID with 400 and accept only `^sess_[A-Za-z0-9_-]{32}$` (or a signed ID). In the widget, treat a non-OK `/api/session` response as a failure and never send null. Delete the existing `unknown_session.json` / `.json` files on the volume.

- **MEDIUM · CONFIRMED · C4 · Async email reports success before the send.** [backend/email_client.py:159](backend/email_client.py#L159)
  *Failure:* quota exhaustion (escalations need no verification, so it can be done on purpose), a MailerSend error or a redeploy kills the daemon thread, and the customer is still promised an email reply.
  *Fix:* send synchronously (the 15s timeout fits in gunicorn's 120s, and escalations are rare) and reply based on the real result. Consider a per-session cap on escalations.

- **LOW · CONFIRMED · `_redact_pii_for_log` redacts only email addresses.** [backend/app.py:889](backend/app.py#L889)
  *Failure:* names (logged twice, raw and in "Leuk je te ontmoeten, <naam>"), phone numbers, postcodes, order numbers and addresses stay in `chat_*.json` for 90 days, in the portal and in every export. CLAUDE.md says the logs are "PII-redacted".
  *Fix:* decide which is intended. Either extend the redaction (`PHONE_NUMBER_RE`, NL/BE postcodes, `state_data['name']`) or correct CLAUDE.md and the privacy statement.

- **LOW · CONFIRMED · Customer names and model output are written to the Railway stdout logs.** [backend/email_client.py:125](backend/email_client.py#L125)
  *Failure:* "Escalation email sent successfully for: Jan de Vries" (also :77, :147, :154), rejected-output snippets (`rag_engine.py:1252, 1266`) and failed-login usernames (`app.py:2241`, where an admin who types the password into the username field gets it logged). None of this falls under `data_retention`.
  *Fix:* log the session or request ID, log only the rejection reason, and drop the username from the failed-login line.

- **LOW · CONFIRMED · portal.db rows are never purged.** [backend/data_retention.py:62](backend/data_retention.py#L62)
  *Failure:* notes, labels and `message_metadata` stay forever after the chat log is deleted. They are orphaned and invisible in the portal.
  *Fix:* in the retention run, delete rows whose `session_id` no longer has a `chat_<id>.json`.

- **LOW · CONFIRMED · Unauthenticated `/portal/<path>` serves all of `portal/`, including `portal/trainingdata/`.** [backend/app.py:2208](backend/app.py#L2208)
  *Failure:* locally, `GET /portal/trainingdata/chat-export-2026-05-19.json` returned 200 (397 KB) without login. Production is not affected, because the folder is gitignored and Railway builds from git.
  *Fix:* serve only `/portal/js/<path>`, and move the exports out of the served tree.

- **LOW · CONFIRMED · The CSV export does not neutralise spreadsheet formulas.** [portal/js/storage.js:505](portal/js/storage.js#L505)
  *Failure:* a chat message `=HYPERLINK(...)` becomes a live formula when an admin opens the export in Excel.
  *Fix:* in `_csvEscape`, prefix values matching `/^[=+\-@\t\r]/` with `'`.

- **LOW · CONFIRMED · Logout does not revoke the admin token.** [backend/app.py:2263](backend/app.py#L2263)
  *Failure:* a copied cookie stays valid for up to 4 h after logout. The cookie is HttpOnly and SameSite=Strict, so it has to be stolen first.
  *Fix:* put a random `sid` in the token and keep a revoked set (or a "valid after" timestamp) in portal.db, or accept the risk.

- **LOW · CONFIRMED · In Zendesk mode the ticket requester is unverified chat input.** [backend/zendesk_client.py:111](backend/zendesk_client.py#L111)
  *Failure:* a visitor escalates with a real customer's email, and the ticket plus the agent replies go to that customer. Inactive today, because production uses email mode.
  *Fix:* use a fixed bot requester and put the email in the body, marked "unverified".

## 4. Phased fix plan

Every fix gets a regression test in **`backend/tests/test_audit_2026_10_regressions.py`**, named after the bug (`test_escalation_email_contains_question`, `test_null_session_id_is_never_persisted`, …). That module posts many chat messages, so it must set `flask_app.limiter.enabled = False`.

### Fase 1 — Production bugs + security 🔴
Do **1.0 first**. Until it is done, running the suite sends real email.

| Step | Fix | Findings |
|------|-----|----------|
| 1.0 | Blank every integration key in `conftest.py` before `import app`. Replace the `generate_response` mocks with `get_answer`/`extract_name`. Add a guard test that asserts the keys are empty. | C2 |
| 1.1 | Email body includes question and name. The triggering message enters `chat_history`. The phone forward carries the number. Shared transcript helper. | C1 |
| 1.2 | Send escalations synchronously and reply on the real result. Set `handoff_done` only on success. | C4, handoff_done |
| 1.3 | Reject a null or invalid `session_id`. In the widget, treat a non-OK `/api/session` as a failure. Delete `unknown_session.json` on the volume. | C5 |
| 1.4 | Check the Railway access log. If it shows the proxy IP: `ProxyFix(x_for=1)`, and exempt `/widget.js` and `/health`. | C3 |
| 1.5 | Frustration gate and `_flow_dead_end` go through `_start_handoff`. Reset `flow_attempts` on flow clear and flow entry. | C6, flow_attempts |
| 1.6 | Phone mention inside the handoff: forward a supplied number, drop `je`, never wipe the state. | phone-re |
| 1.7 | Loop detector: only the last 2 assistant turns, and declines are recorded. | loop detector |
| 1.8 | Remove the `order_match` / Shopify flow (also cut 1 in section 3). The tracking branch uses `extract_order_identifier` directly. | order_match, Shopify flow |

Verify by replaying the reproduced conversations from this report against production (see `pattern_replay_hele_conversatie_na_fix`), not just `/health`.

### Fase 2 — Lower-severity bugs and privacy 🟠
- Router: narrow `TRACKING_INTENT_RE` / the manco pattern. The escape hatch via `classify_intent`. Question detection before number extraction while awaiting a shipment number. Re-run over all chat-export messages first.
- Every canned return goes through `_remember_turn`, with a branch-walking test.
- `CLOSING_RE` skips when the previous turn was a question. `volume_calc` requires units. StatusWeb negations, and a neutral default.
- `check_output` on the unknown path. Email extraction from a sentence, plus an attempt counter.
- Ingestion: retry on a partial embed, no duplicate tail chunk. Per-thread temp file in `save_session_state`.
- Privacy: decide on PII redaction (extend it or correct the docs). Session IDs instead of names in stdout. portal.db orphan purge. `/portal/js/` only. CSV formula escaping.
- `.env.example`: comment out `BRAND_PERSONALITY_*`. Portal language: wire it up or remove it.

Cuts 2–7 and 9–13 from section 3, with no behaviour change, so the existing tests are the safety net.
